# ADR 0004：持久化重试、取消边界与副作用 outbox

- 状态：Accepted
- 日期：2026-07-16
- 决策范围：M4 失败恢复与副作用控制

## 背景

M3 已保证模型不能授权工具，并将高风险调用停在持久化审批点。M4 还需要处理模型供应商
临时故障、进程在任意 checkpoint 后终止、写工具领取后崩溃、重复投递和用户取消。进程内
sleep、只保存在内存中的重试计数，以及在 checkpoint 重放时直接再次调用写工具，都无法
提供这些保证。

## 决策

Provider 故障使用稳定类型区分。429、timeout 和临时 5xx 是可重试错误；结构化输出损坏
及未知异常默认不可重试。可重试失败将来源状态、次数和下一次允许执行的时间持久化到
workflow run，并进入 `RETRYABLE_FAILURE`。恢复请求只有在退避到期后才能先经过持久化的
`RETRY` checkpoint 返回来源状态。默认最多重试三次，延迟采用有上限的指数退避和 jitter；
Worker 不占用线程 sleep。耗尽后进入稳定的 `NON_RETRYABLE_FAILURE`。

注册表内的低风险写工具先在一个事务中创建唯一 tool call 和 `PENDING` outbox，再以短租约
领取。领取事务提交后才允许业务 handler 开始；handler、数据库副作用、outbox 成功状态和
tool call 成功状态在同一事务中提交。进程在领取后终止时，租约到期后可用原幂等键再次领取。
高风险写工具仍必须先审批；批准后才在审批事务中创建并完成唯一 outbox。未来接入数据库
之外的服务时，适配器也必须把同一个幂等键传给远端系统，不能只依赖本地 outbox。

Outbox 保存已通过 schema 校验、仅供执行使用的受控原始参数，不作为日志或 API 导出；结果、
审计和事件负载按工具 PII 策略脱敏。Outbox 是可变的调度状态，而每次入队、领取、成功、失败
或取消都另外写入 append-only `side_effect_event`，从而保留崩溃和重试的完整轨迹。

取消在工具 handler 开始前的持久化边界检查 run 状态，并把待决审批、未开始的 tool call 和
outbox 置为终态。已取消流程不能从 runner 再推进。人工恢复必须提供原因，并清除旧提案后从
`CLASSIFY` 创建新提案；这不会复活被拒绝的原高风险调用。

## 影响

- API/Worker 可在任一已提交状态后重建 runner；活动状态继续推进，暂停或失败状态保持稳定。
- 同一幂等键的 checkpoint 或请求重放复用同一 tool call/outbox，不重复数据库副作用。
- 暂时错误不会忙循环，不可重试错误和重试耗尽都有明确终态。
- 取消保证尚未开始的写工具不启动；同步 handler 一旦跨过开始边界，不做不安全的线程中断。
- outbox 调度状态可更新，但副作用轨迹和审计历史只能追加。
